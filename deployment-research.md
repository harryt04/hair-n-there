# HairnThere deployment research

Historical research: the Actions-oriented requirements and recommendation below are superseded. The current decision is native Vercel Git deployments from main, with no automated tests, pull request process, or external CI/CD. See [the current setup plan](setup-plan.md).

Checked 2026-11-03. Official primary sources only. Scope: a small commercial Next.js App Router site with SSR and a POST contact Route Handler; GitHub connection, branch deployments, previews, and GitHub Actions ownership. Cloudflare findings are included below. No exact prices are quoted.

## Recommendation

**Choose Vercel Pro for the simplest managed Next.js experience, with GitHub Actions running checks, building with Vercel CLI, then deploying the prebuilt output.** Disable native Git-triggered deployment to avoid two deploy pipelines. HairnThere is a commercial business site, so Vercel Hobby is unsuitable even if traffic is tiny. This recommendation is an assessment based on the documented feature support, CI workflow, and plan restriction below.

**Netlify is the strongest alternative when commercial Free eligibility matters.** It supports the required Next.js features and CLI deployments from CI, but account credit exhaustion can pause sites. Budget for a suitable paid plan if uninterrupted business availability matters. **Prefer a paid Render web service if publishing Docker images from Actions becomes a requirement**: it documents registry-image deployment and digest-specific deploy triggers. Railway and DigitalOcean App Platform are also viable container/server hosts. Amplify is a weaker fit because of its documented Next.js version/feature restrictions and lack of manual SSR artifact deployment.

## Baseline: server hosting is required

Next.js documents full feature support for Node.js servers and Docker containers; static exports have limited support. Keep SSR and the POST contact handler on a server/function runtime rather than selecting a static-site-only tier. Docker is optional for this application. [Next.js deployment options](https://nextjs.org/docs/app/getting-started/deploying), [Route Handlers and static export limitations](https://nextjs.org/docs/app/guides/backend-for-frontend).

On general Node/container hosts, framework features run in Next.js itself rather than a host-specific serverless adapter. Image optimization works with `next start`; ephemeral or multiple instances require attention to cache persistence/coordination, Server Action keys, and deployment version consistency. Streaming also depends on the proxy path passing responses without buffering. These are operational considerations, not reasons to require Docker. [Next.js self-hosting](https://nextjs.org/docs/app/guides/self-hosting).

## Cloudflare (parent research)

- **Git/branches:** Workers Builds connects to GitHub and automatically builds/deploys pushes; production branch and nonproduction branch behavior are configurable. This provides the requested repository/branch experience. [Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/), [Build branches](https://developers.cloudflare.com/workers/ci-cd/builds/build-branches/).
- **Next.js runtime:** Current documentation recommends vinext, a beta Vite-based reimplementation of the Next.js API surface. Test feature compatibility rather than equating Git integration with identical Next.js runtime behavior. [Next.js integration](https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/).
- **Actions:** The official Wrangler Action supports deployment from GitHub Actions. Use that instead of overlapping native build/deploy triggers when Actions owns CD. [Actions guide](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/).
- **Docker alternative:** Cloudflare Containers runs a normal Docker image behind Worker/Durable Object routing. Actions can deploy using Wrangler with a Dockerfile or a supported registry image. Container deployments need separate staging environments rather than assuming ordinary Worker version URLs preview the full container app. This adds lifecycle, scaling, cache, and sleep policy decisions. [Containers setup](https://developers.cloudflare.com/containers/get-started/), [Container deployment](https://developers.cloudflare.com/containers/guides/deploy/).
- **Billing:** Containers requires Workers Paid and adds resource/associated-service usage charges. [Pricing](https://developers.cloudflare.com/containers/platform/pricing/).

## Vercel

- **Features:** Native Next.js integration deploys SSR to Functions and supports streaming through Route Handlers and React Server Components; suitable for the contact POST endpoint. No Docker image is needed for this deployment path. [Next.js on Vercel](https://vercel.com/docs/frameworks/full-stack/nextjs).
- **Git/previews:** Git integration automatically deploys pushes and creates preview deployments for proposed changes. [Git deployment workflow](https://vercel.com/docs/git).
- **Actions ownership:** Official workflow uses `vercel pull`, `vercel build`, then `vercel deploy --prebuilt`; add `--prod` to build/deploy for production. Put deployment after successful checks. Set `git.deploymentEnabled: false` in `vercel.json` to disable competing native deploys. CLI previews remain available, but Git-provider metadata and branch-specific URLs differ from native integration; prebuilt builds also need explicit handling of any system environment variables required at build time. [Official GitHub Actions guide](https://vercel.com/kb/guide/how-can-i-use-github-actions-with-vercel).
- **Commercial caveat:** Hobby is restricted to personal, noncommercial use. Use Pro or Enterprise for HairnThere. Hobby also cannot deploy private organization repositories. [Hobby plan](https://vercel.com/docs/plans/hobby), [Git restrictions](https://vercel.com/docs/git).

## Netlify

- **Features:** OpenNext adapter supports App Router, SSR, Route Handlers, Server Actions, ISR, streaming, and image optimization. Current adapter supports Next.js 13.5 onward. Edge-runtime SSR executes in the Functions region under Node; Node middleware cannot use filesystem/C++ addons. Header/redirect ordering and some rewrites differ from standalone Next.js. No Docker deployment artifact is required. [Next.js support and limitations](https://docs.netlify.com/build/frameworks/framework-setup-guides/nextjs/overview/).
- **Git/previews:** Connected Git builds support production, branch deployments, and PR Deploy Previews. [Deploy Previews](https://docs.netlify.com/deploy/deploy-types/deploy-previews/), [Build controls](https://docs.netlify.com/build/configure-builds/stop-or-activate-builds/).
- **Actions ownership:** Stop Netlify builds, then use its CLI on the Actions runner after checks. Stopping builds also stops automatic branch/PR previews and build hooks; CLI/API manual uploads remain possible, so implement preview deployments in Actions too. `netlify deploy --prod` builds and uploads the adapter-produced assets/functions; alternatively run `netlify build` then upload the resulting output without another build. Uploading `.next` as ordinary static files is insufficient for SSR. [Build controls](https://docs.netlify.com/build/configure-builds/stop-or-activate-builds/), [CLI guide](https://docs.netlify.com/api-and-cli-guides/cli-guides/get-started-with-cli/), [CLI deploy reference](https://github.com/netlify/cli/blob/main/docs/commands/deploy.md).
- **Commercial caveat:** Netlify explicitly permits commercial projects on Free. Its older announcement's numerical quotas are obsolete; consult current credit-based plans. Current pricing warns that reaching monthly limits pauses sites, potentially all projects on the account. Free has hard limits; paid credit recharge is configurable. [Commercial permission](https://www.netlify.com/blog/introducing-netlify-free-plan/), [Current pricing/limits](https://www.netlify.com/pricing/).

## Railway

- **Features/Docker:** Official Next.js guide covers GitHub, CLI, standalone output, and Dockerfile deployments. Normal Node/container hosting supports the SSR/contact requirements; apply the shared self-hosting considerations above. Docker is optional; CLI source uploads are built remotely using Railpack or the Dockerfile. [Next.js guide](https://railway.com/guides/nextjs), [CLI deployment](https://docs.railway.com/cli/deploying).
- **Git/CI:** Connected-branch pushes deploy automatically. “Wait for CI” delays Railway's own build/deploy until GitHub Actions workflows finish; it does **not** transfer build ownership to Actions. Requires a workflow triggered on `push`. It evaluates workflow conclusions, ignores neutral/skipped runs, and has cancellation exceptions, so do not treat it as proof every mandatory step ran. For strict Actions ownership, disable autodeploy and invoke `railway up` after checks; Railway still builds the uploaded source remotely. [Autodeploy and Wait for CI](https://docs.railway.com/deployments/github-autodeploys), [CLI](https://docs.railway.com/cli/deploying).
- **Previews:** PR environments provision isolated copies and are removed when PRs close/merge. They consume resources; Actions can also create/delete environments. [PR environments](https://docs.railway.com/environments), [Actions environment example](https://docs.railway.com/cli/deploying).
- **Commercial caveat:** Railway recommends Pro for commercial applications; this is a recommendation rather than Vercel's explicit Hobby prohibition. Subscription plus resource usage can exceed included allowance. Private Docker registry deployments require Pro. [Pricing FAQ](https://docs.railway.com/pricing/faqs), [Docker image/plan requirements](https://docs.railway.com/quick-start). For Actions-built images, use a registry-backed service rather than expecting `railway up` to upload a local image; Railway also provides optional [image auto updates](https://docs.railway.com/deployments/image-auto-updates).

## Render

- **Features:** Deploy full Next.js as a Node web service (`build`, then `start`), not a static site. Docker is optional; the general Next.js self-hosting considerations apply. [Next.js deployment guide](https://render.com/docs/deploy-nextjs-app).
- **Git/CI:** Connected branch pushes normally rebuild/deploy. “After CI Checks Pass” gates Render's build on repository checks; zero detected checks prevents deployment, while GitHub `neutral` and `skipped` conclusions count as passed. For Actions-owned release orchestration, turn autodeploy Off and trigger deployment after required jobs. [Deploy controls](https://render.com/docs/deploys).
- **Actions-built Docker:** Actions can build/push to GHCR or another supported registry, then trigger the image-backed service through a deploy hook/API. A hook's `imgURL` can select an immutable digest. Image-backed services do not use Git autodeploy; a registry push alone is insufficient. [Registry deployment and hooks](https://render.com/docs/deploying-an-image), [Autodeploy restrictions](https://render.com/docs/deploys).
- **Previews:** Git-backed PR previews are supported. Image previews can be created through API/Actions but must be explicitly deleted; they are billed as compute. [Service/image previews](https://render.com/docs/service-previews).
- **Production caveat:** Render explicitly says not to use Free instances for production. Free web services sleep after 15 idle minutes and take about a minute to wake. Choose paid compute for HairnThere. [Free limitations](https://render.com/docs/free).

## AWS Amplify Hosting

- **Features:** The official support page currently specifies Next.js 12–15, including SSR, API routes, app directory, images, and ISR. It lists streaming, on-demand ISR, Edge API routes/Edge middleware, and `unstable_after` as unsupported. A Node contact handler fits the documented server-side feature set, but test the exact Next.js version; do not assume Next.js 16 support. Docker is not the normal Amplify Hosting deployment artifact. [Support matrix](https://docs.aws.amazon.com/amplify/latest/userguide/ssr-amplify-support.html).
- **Git/Actions:** For a repository-connected app, disable branch `enableAutoBuild`, then have Actions invoke `StartJob` with `RELEASE` after checks. This is an inferred integration of the documented APIs: Actions gates the release; Amplify still fetches/builds the branch. `RELEASE` builds the latest branch change, so account for newer commits arriving after the tested SHA. Crucially, manual ZIP/S3 artifact deployments do **not** support SSR; they are not a substitute for deploying a prebuilt SSR app from Actions. [Branch controls](https://docs.aws.amazon.com/amplify/latest/APIReference/API_UpdateBranch.html), [StartJob](https://docs.aws.amazon.com/amplify/latest/APIReference/API_StartJob.html), [Manual SSR restriction](https://docs.aws.amazon.com/amplify/latest/userguide/manual-deploys.html).
- **Previews:** PR web previews exist, but public repositories requiring an IAM service role (including WEB_COMPUTE SSR) have restrictions; a private repository is the straightforward fit. [Preview security](https://docs.aws.amazon.com/amplify/latest/userguide/pr-previews.html).
- **Commercial/billing:** A usage-billed AWS option for business workloads; build minutes, storage, transfer, SSR requests/duration and optional services are separate meters. Free-tier eligibility is not a permanent zero-cost hosting guarantee. [Official pricing](https://aws.amazon.com/amplify/pricing/).

## DigitalOcean App Platform (optional alternative)

- **Features/Docker:** Run Next.js as a web service/container, applying the shared self-hosting considerations. Official Next.js template uses Docker; App Platform also builds source repositories. Static-only Free hosting cannot run the SSR/contact endpoint. [Official template](https://github.com/nextjs/deploy-digitalocean), [Component/pricing model](https://docs.digitalocean.com/products/app-platform/details/pricing/).
- **Git/Actions/previews:** Official Actions guide covers source deployment, Actions building/pushing a Docker image to GHCR followed by deployment, and creating/deleting separate PR preview apps. Place deploy jobs after checks and disable competing source/image auto-deployment in the app configuration. Preview apps are separate running resources, so include cleanup and their cost. [Actions guide](https://docs.digitalocean.com/products/app-platform/how-to/deploy-from-github-actions/), [Deployment controls](https://docs.digitalocean.com/products/app-platform/how-to/manage-deployments/).
- **Registry caveat:** Public/private DOCR, Docker Hub, and GHCR images are supported. The documented image push-triggered autodeploy option is for DOCR; use the explicit Actions deployment workflow for GHCR. [Container image deployment](https://docs.digitalocean.com/products/app-platform/how-to/deploy-from-container-images/).
- **Commercial/billing:** Select paid web-service compute; container size/count and bandwidth determine cost. This is a conventional paid business hosting option rather than a personal-use-only free plan. [Pricing](https://docs.digitalocean.com/products/app-platform/details/pricing/).

## Suggested pipeline policy (assessment)

Use one deployment owner: GitHub Actions. Run install, lint/typecheck, tests, then the host-specific build/deploy job with explicit successful-job dependencies. Pushes to `main` deploy production; trusted PRs get preview deployments, with cleanup where required. Disable overlapping native deploy triggers. If Docker is adopted, Actions should build/push only after checks and deploy an immutable image digest. For the current small site, start without Docker on Vercel Pro or Netlify; Docker adds value primarily when portability or a container-host requirement justifies it.

The contact handler still needs an actual email/delivery service and server-side configuration; hosting SSR does not itself deliver form submissions. Validate that endpoint on the chosen host before launch. No deployment or account changes were performed for this research.
